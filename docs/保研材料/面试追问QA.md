## 一、通用问题

### Q1. 简单介绍一下这个项目。
**答**：这是一个面向视障人群的 Android 无障碍出行辅助平台，核心是两大功能：**语音导航**和**文字识别**。整体是一条"语音感知—语义理解—空间定位—视觉感知—多通道反馈"的端云协同多模态流水线：用户说话，系统流式语音识别并提取目的地，规划步行路线后逐向语音+震动播报；用户拍照，系统云端多模态模型识别文字并朗读。我是三人团队的核心开发成员，负责**多模态播报仲裁机制**和**整体架构**两块。项目已登记软著，拿了 2026 年计设大赛北京市二等奖，并以北京市级大创项目验收合格。

### Q2. 你个人具体做了哪些部分？
**答**：① 多模态播报仲裁器——用优先级抢占解决多事件并发播报冲突；② 导航六态状态机与页面流程；③ MVVM 三层分层架构与手动依赖注入容器；④ 参与了流式语音识别、TTS 双引擎、OCR 管线与无障碍适配的集成。队内分工是另外两位同学分别负责地图路线与界面细节、测试与文档（**按实际分工调整**）。

### Q3. 这个项目最大的创新点是什么？
**答**：我认为是**多模态播报仲裁机制**。一个出行辅助系统里，导航转向、障碍物、红绿灯、OCR 结果、系统信息会并发出现，如果不调度，语音会互相打断。我把所有播报事件统一建模，定义"障碍 > 导航 > OCR > 信息"的优先级抢占规则，并让 TTS、震动、文案分别抽象成接口，做到仲裁策略可单测、平台副作用可替换。这其实是一个"**输出通道资源调度**"问题，和音频焦点、通知优先级是同一个思想。

### Q4. 项目中遇到的最大难点是什么？怎么解决的？
**答**：最大的难点是**多语音源的并发冲突**。最初各功能各自播报，会出现导航播到一半被 OCR 结果打断、用户听不清的情况。解决思路是收敛：所有播报必须经过仲裁器这一个入口，用优先级抢占保证高优先级事件（比如障碍物）能插队，同时保证低优先级事件不丢失、播报完自动回落到信息级。另一个难点是百度 SDK 初始化不稳定，我用一个"四维一致性状态机 + 超时降级"来保证不阻塞启动。

### Q5. 这个项目和你申请的方向（人工智能/多模态）有什么关系？
**答**：三点相关：① 系统本身就是多模态感知到多模态反馈的闭环，涉及语音、图像、定位、触觉四类模态的协同；② 我的核心工作是**多模态输出调度**，可以延展到多模态融合、跨模态对齐等更一般的问题；③ 我熟悉了流式 ASR、LLM 意图提取、多模态 OCR 这类前沿模型的工程化落地，知道它们在真实移动端约束下如何取舍。

## 二、技术深挖（核心模块）

### Q6. 仲裁器的优先级抢占具体怎么实现？【✅ 必考】
**答**：用 sealed class 定义事件类型（障碍/转向/红绿灯/到达/OCR/信息），优先级用枚举 ordinal 排序：障碍 > 导航 > OCR > 信息。规则是：如果正在播报，新事件优先级**更高或同级**就 `stop()` 抢占；播报完成后，如果自己仍然是最新事件，就回落到信息级继续播。底层用协程 + `speakAndWait`（等 TTS 播完再返回）保证顺序。

### Q7. 为什么不直接用系统自带的音频焦点（Audio Focus）？【❓ 加分题】
**答**：音频焦点解决的是"跨应用"抢音频的问题，解决不了"**同一个应用内部**多个事件源谁先播"的问题；而且我们的播报还包括震动通道，音频焦点管不到。所以我把它当作一个**应用内事件调度**问题来解决，仲裁器统一管语音+震动，音频焦点是另一个层面的东西（实际上也更适合在应用层之上做合规）。

### Q8. 为什么用流式 ASR，不用一次性录音再识别？【✅】
**答**：出行场景用户要的是"边说边出结果、尽快开始导航"的低延迟体验。一次性识别要等用户说完、录完整段再上传，端到端延迟高。我们用的 DashScope `paraformer-realtime-v2` 是双工 WebSocket 流式接口，按 100ms 一帧（3200 字节 PCM）持续上传，识别结果边出边回，配合能量检测自动判断"说完了"，体验上接近免按键。

### Q9. 静音检测的 RMS 阈值为什么取 300？【✅ 可深挖】
**答**：阈值是经验值，通过真机在不同环境（安静室内、街道）实测标定的：用 16kHz/16bit 单声道 PCM，静音时采样值很小，RMS 通常远低于阈值；正常说话会明显超过。设 300 是在"别把环境底噪当语音"和"别把轻声说话当静音"之间取的平衡。**局限我也清楚**：它对突发噪声（鸣笛、施工）鲁棒性不够，这是后续想换成更鲁棒 VAD 的原因——这属于诚实且专业的回答。

### Q10. 为什么用大模型提取目的地，不用关键词/词典？【✅】
**答**：口语里目的地夹杂大量冗余（"去离家最近的家乐福超市"），且地名是开放集合，词典和规则难以穷举。我用 qwen-turbo 做提取，系统提示词限定"只返回地址本体"并给示例，`temperature=0.1` 控制随机性，`max_tokens=100` 限制长度，空结果回退用 ASR 原文，保证绝不因 LLM 失败而中断交互。

### Q11. POI 检索和地理编码是怎么配合的？【✅】
**答**：两级策略：先在周边 50km 半径做 POI 就近检索（按距离升序），结果为空再回退到全国地理编码。还处理了一个 SDK 兼容 bug——部分机型 `PoiInfo.distance` 恒为 0，我改用 `Location.distanceBetween` 实时算直线距离，并对"名称+经纬度"去重，避免重复候选。

### Q12. 导航为什么用状态机？六态怎么定义？【✅】
**答**：导航流程的状态边界很清晰——待机、监听、规划路线、导航中、暂停、到达。用显式状态机，页面 UI 可以直接按状态切换子界面，非法跳转（比如没规划完就进入导航中）在编译/设计层面就被排除。录音协程放在父级作用域，避免切界面导致会话中断。

### Q13. OCR 为什么做端侧压缩再上传？【✅】
**答**：CameraX 拍出来的原图很大，直接上传会拉高延迟和流量。我们端侧做旋转校正、最长边压到 1024px、JPEG 80%，再转 Base64 上传云端多模态模型。在保证识别可读性的前提下，显著降低传输成本——这就是"端云协同"在视觉通道的落地。

### Q14. TTS 为什么做双引擎？【✅】
**答**：主引擎是百度 AIPE 在线 TTS，音色和效果更好，但它依赖网络。备用引擎是系统 TextToSpeech，作为弱网/离线兜底。两个引擎的语速设置通过归一化映射同步。这样即使云端 TTS 挂了，播报也不会断——这对视障用户是可用性红线。

### Q15. 无障碍是怎么做的？【✅】
**答**：三层：① 交互层——高对比深色主题（纯黑底+金色主色）、大字号，专为低视力设计；② 语义层——全量 `contentDescription`/`semantics`/`liveRegion`/`traversalIndex` 标注，保证 TalkBack 读屏可操作；③ 反馈层——语音+震动双通道。我还按 WCAG 的 POUR 四原则做了发布前验收清单。

## 三、高风险区应对（⚠️ 最重要，请重点练习）

### Q16. 你的障碍物检测是怎么实现的？【⚠️ 诚实策略】
**答**（如实说）：目前 `ObstacleDetectionService` 和 `TrafficLightService` 是**模拟数据驱动的验证实现**——按 8s/15s 周期生成事件，用于打通"感知→仲裁→播报→震动"全链路。它验证的是**交互链路**的正确性，而不是检测算法的准确率。我把它设计成了可插拔的感知服务抽象，后续要接入真实视觉检测（YOLO 系列端侧模型），只需要替换感知实现、不需要改仲裁和反馈层。**我已经在规划这条路线。**

> **为什么这么答**：教授的追问大概率是"用什么模型？mAP 多少？真机测过吗？"——模拟实现一旦被戳穿，其他真实工作也会被连坐。主动说出边界 + 给出替换路径，反而显得诚实且有工程判断力。**千万不要说"基于视觉的障碍物检测已实现"。**

### Q17. 有没有性能数据？启动耗时、ASR 延迟多少？【⚠️ 诚实策略】
**答**：我们建立了性能测试用例（启动、交互延迟、功耗），但**还没有形成正式的量化基准**，所以我不提供具体数字。我能说的是设计上的保证：流式识别 100ms/帧的传输粒度、OCR 端侧压缩、路线规划 15s 超时兜底。这正是我计划在下一步补齐的实验内容。

> 若被逼问具体数字：明确说"没有实测，不编数字"。编一个数字被追问细节会立刻穿帮。

### Q18. 网络安全配置允许明文流量、还信任用户证书，这是安全隐患吧？【⚠️ 技术债务】
**答**：是的，这是项目的已知技术债务。当时为了调试第三方 SDK 方便开了明文与用户证书信任，**生产发布前必须收紧**：关闭明文、取消信任用户证书、按域名白名单放行必要的云端接口。这个我列进了后续加固计划。你能指出这点很专业（顺势表达学习态度）。

### Q19. 隐私政策里写"用 Google ML Kit 做本地文字识别"，但实际用的是火山云端 OCR？【⚠️ 文案不一致】
**答**：这是历史遗留文案，和实际实现不一致——我们实际用的是云端多模态模型，识别在云端完成。隐私文案必须与实际数据流一致，这个 bug 需要修复：要么改文案，要么按文案实现端侧识别。**这暴露了一个合规意识问题，也是我需要改进的地方。**（如实承认 + 给出正确做法）

### Q20. 数据都存在 SharedPreferences，为什么不用数据库？【⚠️ 可辩护】
**答**：当前业务数据的体量和结构（设置项、隐私同意状态、位置键值）用 SharedPreferences 足够，复杂度最低。但项目里已经留了注释——如果需要历史轨迹、POI 收藏这类结构化、可查询的数据，会引入 Room。这是一个**按需演进**的决策，不是能力缺失。

## 四、理论与对比追问

### Q21. 为什么设计"语音+震动"双通道？【❓ 理论题】
**答**：依据 Paivio 的双编码理论——言语和非言语信息由两套符号系统加工，双通道呈现能增强信息保持与可辨性。对出行场景，环境噪声会淹没语音，此时震动是独立通道（障碍=两短震、转向=一长震、红绿灯=三短震），用户不必"只听"也不会漏。同时逐向播报控制单次信息量，对应 Sweller 的认知负荷理论，把"感知-规划"负担外置给系统。

### Q22. 和 NavCog、Crosswatch 这些论文里的系统比，你差在哪、好在哪？【❓ 加分题】
**答**：NavCog 用的是精确室内定位（WiFi/蓝牙），我们主打室外步行、GPS+POI 方案，精度上确实不如；Crosswatch 专注路口视觉识别，我们的路口/信号灯感知还在模拟阶段。但我们有两点不同：① 我们把"多模态**输出调度**"（仲裁器）当独立问题做了系统化设计，这是很多单点方案没处理的；② 我们把大语言模型引入目的地提取，解决了开放地名口语解析问题。这些都是可以继续深入的切口。

### Q23. "多模态"在你的系统里到底指什么？【❓ 澄清题，防止被"假多模态"质疑】
**答**：要区分两种：一是**理解侧的多模态**（多模态大模型做图像+文本理解），二是**系统级的多模态闭环**（语音、视觉、定位、触觉四种模态在感知与反馈两端协同）。我们的系统属于第二种为主、第一种为辅：多模态大模型用于 OCR，而系统的骨架是四类模态的感知-反馈闭环。仲裁器处理的正是这个闭环里"多模态输出如何有序呈现"的问题。

### Q24. 为什么不直接接入商用语音助手/地图 App，自己做的意义在哪？
**答**：三个理由：① 商用语音助手不是为"行走中的视障用户"设计的，没有震动通道、没有针对读屏的语义优化；② 我们的仲裁机制让"导航+障碍+OCR"能统一有序呈现，这是拼接多个 App 做不到的；③ 面向特定人群的可用性细节（高对比、语义标注、双通道）需要按无障碍规范专门打磨。

## 五、扩展方向问答（展示研究潜力）

### Q25. 如果你继续做，最想先做什么？
**答**：**真实感知接入**。框架已经就绪，把 YOLO 类端侧目标检测接入障碍物/交通灯感知，补上"感知"这最后一环，然后做一轮真实视障用户的实地可用性研究，用任务完成率和 NASA-TLX 主观负荷量表量化"多通道反馈到底有没有降低认知负荷"——这个实证能回答项目最核心的研究假设。

### Q26. 端侧和云端怎么划分才合理？
**答**：原则是"**时延敏感、隐私敏感的任务尽量端侧，重计算放云端**"。流式 ASR 可以先端侧做 VAD/端点检测、云端做识别（或参考 WeNet 做端侧 ASR）；OCR 可以在端侧跑轻量检测（先定位文本区域）再云端精细识别。端云两级理解能在弱网下降级为纯端侧，这是下一步的架构方向。

### Q27. 怎么验证"多模态播报仲裁降低了认知负荷"？
**答**：设计对照实验：同一批视障被试，一组用"无仲裁（各事件各自播报）"，一组用"仲裁串行播报"，在真实路段测任务完成率、出错次数，主观上用 NASA-TLX 量表测负荷，用 SUS 测可用性。还可以测量转弯前播报与用户动作的时延。这是把工程贡献升级为学术贡献的标准路径。

## 六、回答技巧与注意事项

1. **关键词精确**：能随口说出"100ms/帧""RMS 阈值 300""15s 超时""8s/15s 周期"这类具体数字，比空谈概念可信得多——这些都是真实代码里有的，随便深挖。
2. **主动给"诚实边界"**：障碍物模拟、无性能数据、明文网络这三个雷，**自己先讲**，配一句"这是已知局限/技术债务 + 我的改进计划"，比被教授挖出来体面得多。
3. **把缺点转成研究问题**："还没有实测"→"这正是下一步要做的对照实验"，展示的不是补锅，而是研究规划能力。
4. **不要编造**：任何不存在的数字（mAP、延迟、用户量）一旦被追问细节必然穿帮，还会连累真实部分的可信度。
5. **对齐申请方向**：教授如果是做多模态/人机交互的，多往"多模态输出调度""认知负荷实证"上引；如果是做系统/移动计算的，多往"端云协同""状态机""SDK 工程化"上引。
